1. ROLE, MISSION, AND HYBRID STACK STRATEGY
--------------------------------------------------------------------------------
Act as a Principal Frontend Systems Architect and Graph Visualization Engineer.
Build Phase 1 of an offline-first, visual partnership management application
designed for social sector / NGO teams.

The application models institutional partnerships as a bottom-to-top directed
multiplex network (multiple parallel color-coded relationship branches between
the same pair of organizations) and derives honest quantitative progress
metrics directly from live graph topology without subjective 1-to-5 ratings.

CRITICAL ARCHITECTURAL CONTEXT: RUST + TYPESCRIPT / NODE.JS HYBRID DESIGN
This product is intentionally NOT built in 100% pure Rust (pure Rust GUI
frameworks require heavy custom 2D curved-edge hit-testing, port-aware layered
graph drawing, and HTML-over-SVG button portals), and it is NOT packaged as a
pure Node.js / Electron app (which bundles Chromium and Node.js into a heavy
desktop installer).

Instead, we are building a clean two-layer hybrid desktop architecture:

  Layer 1 — Node.js Toolchain + TypeScript / React Canvas (BUILD THIS NOW):
    Node.js serves strictly as the development and Vite bundling toolchain to
    compile a pure TypeScript, React, React Flow, and elkjs frontend. This
    layer owns all 2D visual rendering, parallel Bezier curve routing, inline
    tick/cross buttons, bottom-to-top layered layout, anti-overlap geometry,
    and pure quantitative graph calculations.

  Layer 2 — Rust Desktop Shell + Local SQLite via Tauri v2 (PHASE 2 TARGET):
    Once Phase 1 is verified in Vite, this exact compiled frontend bundle will
    drop directly into a Tauri v2 Rust desktop app (`src-tauri/`) running on
    Windows WebView2. Rust will own native OS file dialogs, compact offline
    packaging, and atomic reads/writes to a single local SQLite workspace file
    holding multiple interconnected Workbooks.

YOUR MANDATE IN PHASE 1:
Build a complete, polished, fully interactive single-workbook prototype using
Vite + TypeScript + React Flow + elkjs, while strictly enforcing the normalized
data schema, async repository boundary, pure engine isolation, and webview-safe
rules below so Phase 2 requires ZERO rewrite of any UI, graph, or engine file.

3. NORMALIZED RELATIONAL DATA SCHEMA (src/types/schema.ts)
--------------------------------------------------------------------------------
CRITICAL RULE: Never embed organization profiles directly inside a workbook
node. Store data in normalized relational collections that map 1-to-1 to SQLite
tables in the Phase 2 Rust backend, separating master entities from
per-workbook placements and keeping graph topology decoupled from coordinates.

Implement these exact TypeScript interfaces in `src/types/schema.ts`:

  export type EntityCategory =
    | 'ngo'
    | 'csr'
    | 'government'
    | 'institution'
    | 'community'
    | 'other';

  export type BranchType = 'green' | 'white' | 'yellow';
  // green  = Financial / CSR funding only
  // white  = Direct working relationship (venue, attendance, co-host, goodwill)
  // yellow = Network bridge / referral / amplification gateway

  export type BranchStatus = 'pending' | 'tick' | 'cross';
  // pending = Planned outreach or awaiting reply (dashed normal hue)
  // tick    = Verified partner action / commitment (solid glowing neon hue)
  // cross   = Declined / stalled outreach (faded gray or grayish-green)

  export interface Entity {
    entityId: string;
    name: string;
    category: EntityCategory;
    globalNotes: string;
    createdAt: string;
  }

  export interface Workbook {
    workbookId: string;
    title: string;
    description: string;
    targetBudgetInr: number;
    status: 'active' | 'archived' | 'draft';
    createdAt: string;
    updatedAt: string;
  }

  export interface Placement {
    placementId: string;
    workbookId: string;
    entityId: string;
    isRootNgo: boolean;
    // Geometry (mutated only by manual drag, local anti-overlap, or Tidy Up)
    x: number;
    y: number;
    width: number;
    height: number;
  }

  export interface Branch {
    branchId: string;
    workbookId: string;
    sourcePlacementId: string;
    targetPlacementId: string;
    type: BranchType;
    status: BranchStatus;
    valuePct?: number; // Strict percentage of targetBudgetInr (e.g., 25 => M25)
    note: string;
    updatedAt: string;
  }

  export interface WorkbookLink {
    linkId: string;
    sourceWorkbookId: string;
    targetWorkbookId: string;
    relationLabel: string;
    note: string;
  }

  export interface WorkspaceState {
    schemaVersion: 1;
    activeWorkbookId: string;
    entities: Record<string, Entity>;
    workbooks: Record<string, Workbook>;
    placements: Record<string, Placement>;
    branches: Record<string, Branch>;
    workbookLinks: Record<string, WorkbookLink>; // Reserved for Phase 2 Overview Map
  }

4. RUST / TAURI STORAGE BOUNDARY AND WEBVIEW GUARDRAILS
--------------------------------------------------------------------------------
Enforce these four architectural rules strictly across the entire codebase:

4.1 Async WorkspaceRepository Interface (src/storage/workspaceRepository.ts)
Every load, save, export, and import action MUST flow exclusively through an
async `WorkspaceRepository` interface:

  export interface WorkspaceRepository {
    loadWorkspace(): Promise<WorkspaceState | null>;
    saveWorkspace(state: WorkspaceState): Promise<void>;
    exportWorkspaceFile(state: WorkspaceState): Promise<void>;
    importWorkspaceFile(): Promise<WorkspaceState | null>;
  }

- Phase 1 Implementation (`src/storage/localStorageRepository.ts`):
  Persists validated `WorkspaceState` JSON to `localStorage` and implements
  JSON file download/upload with runtime schema validation.
- Phase 2 Stub (`src/storage/tauriSqliteRepository.ts`):
  Create a clean stub file implementing `WorkspaceRepository` (commented with
  the planned Tauri v2 `invoke()` commands: `load_workspace`, `save_workspace`,
  `export_workspace_json`, `import_workspace_json`) and a factory selector in
  `src/storage/index.ts` that detects Tauri runtime (`'__TAURI_INTERNALS__' in
  window`) or defaults to `LocalStorageRepository` in Phase 1.
- ZERO direct `localStorage`, `FileReader`, or anchor-download code anywhere
  inside React components, toolbar buttons, or Zustand actions.

4.2 Pure Domain Engine Isolation (src/engine/*)
Every module inside `src/engine/` (`layout.ts`, `overlap.ts`, `metrics.ts`,
`parallelEdges.ts`) MUST contain pure TypeScript functions with zero imports
from `react`, `window`, `document`, or `localStorage`.

4.3 Webview-Safe State Navigation
Use React/Zustand state (`activeView: 'canvas' | 'opening'`) for navigation.
Do NOT install React Router or rely on `window.history.pushState` URL path
routing, which complicates local webview protocol loading inside Tauri.

4.4 Multi-Workbook Filter Hygiene
All selectors, metrics calculations, and layout functions must filter strictly
by `state.activeWorkbookId` so adding multiple Workbooks in Phase 2 works
immediately without refactoring selectors.

6. PERSISTENT DRAGGING, ANTI-OVERLAP, AND BOTTOM-TO-TOP TIDY UP
--------------------------------------------------------------------------------
6.1 Persistent Zero-Snap-Back Dragging
- Dragging any node updates its `(x, y)` live and commits the dropped position
  permanently to `state.placements` and `WorkspaceRepository`.
- NEVER run a continuous background force simulation or reactive `useEffect`
  that snaps dragged nodes back to old layout coordinates.

6.2 Local Rectangular Anti-Overlap Guard (`src/engine/overlap.ts`)
- On `onNodeDragStop` and whenever a new node is added, execute a fast,
  deterministic bounding-box overlap removal pass using real card widths and
  heights plus a `24px` safety margin on all four sides.
- Keep the user's dragged card anchored exactly where dropped, nudging only
  colliding neighboring cards apart by the smallest horizontal/vertical
  displacement required until zero rectangles overlap. Uninvolved cards stay
  completely stationary.

6.3 Bottom-to-Top Tidy Up Button (`src/engine/layout.ts`)
- Uses `elkjs` configured explicitly for bottom-to-top hierarchies:
    "elk.algorithm": "layered"
    "elk.direction": "UP"
    "elk.edgeRouting": "SPLINES"
    "elk.spacing.nodeNode": "72"
    "elk.layered.spacing.nodeNodeBetweenLayers": "125"
    "elk.layered.crossingMinimization.strategy": "LAYER_SWEEP"
    "elk.layered.nodePlacement.strategy": "NETWORK_SIMPLEX"
- Read-Only Topology Guarantee: The layout function takes `placements` and
  `branches` as read-only inputs and returns a `Record<placementId, { x, y }>`
  map. It NEVER deletes, alters, or disconnects any branch.
- Smooth Transition: Interpolate cards smoothly over ~400ms from old `(x, y)`
  to new Tidy Up `(x, y)`, save the updated coordinates through
  `WorkspaceRepository`, fit the viewport gently, and immediately return full
  control to free manual dragging.
- Handle disconnected nodes (zero edges) gracefully without crashing ELK.

7. PURE QUANTITATIVE METRICS ENGINE (src/engine/metrics.ts)
--------------------------------------------------------------------------------
Compute all seven metrics purely from the active Workbook's placements and
branches. Zero subjective 1-to-5 scores:

1. `funding`:
   - `securedPct`: sum of `valuePct` on ticked green branches
   - `pendingPct`: sum of `valuePct` on pending green branches
   - `declinedCount`: count of crossed green branches
   - `securedInr`: `(securedPct / 100) * workbook.targetBudgetInr`

2. `directRelationships` (white branches whose source is the root NGO):
   - `confirmedCount` (tick), `pendingCount` (pending), `declinedCount` (cross)
   - `confirmationRatePct`: `confirmed / (confirmed + declined) * 100` (0 if
     denominator is 0)

3. `yellowBridges`:
   - `confirmedCount` (tick), `pendingCount` (pending), `declinedCount` (cross)

4. `ownedConversions`:
   - `referredNodeCount`: unique non-root placements with >= 1 incoming ticked
     yellow branch
   - `convertedNodeCount`: unique non-root placements holding BOTH >= 1
     incoming ticked yellow branch AND >= 1 incoming ticked white branch from
     the root NGO
   - `conversionRatePct`: `converted / referred * 100`

5. `multiThreadTargets`:
   - `doubleThreadCount`: placements with confirmed `yellowInDegree === 2`
   - `tripleThreadCount`: placements with confirmed `yellowInDegree === 3`
   - `quadPlusThreadCount`: placements with confirmed `yellowInDegree >= 4`
   - `triplePlusNames`: array of entity names with `yellowInDegree >= 3`

6. `topAmplifier`:
   - For every non-root placement `u`, run BFS along outgoing ticked yellow
     edges to compute unique confirmed downstream reachable nodes.
   - Return entity name, direct ticked yellow out-degree, and total unique
     confirmed downstream reach count.

7. `bridgeConcentration`:
   - Compute `R_total`: set of unique non-root placements reachable from the
     root NGO via paths of length >= 2 using ticked yellow branches.
   - Remove the highest-reach non-root bridge node `b` and recompute
     `R_without_b`.
   - `concentrationPct = ((|R_total| - |R_without_b|) / |R_total|) * 100`.
   - Return bridge entity name and `concentrationPct` (0% if `|R_total| === 0`).
